# CLAUDE.md — banko-ai-assistant

This file orients any Claude Code session (or human contributor) picking up this repo cold.

## What this project is

Banko AI Assistant is a **production-ready agentic RAG demo** for a fictional bank. It demonstrates retrieval-augmented generation, multi-agent orchestration on LangGraph, durable workflow checkpointing on CockroachDB, multi-provider LLM support, and (in v1.1 of the Spending Coach work) streaming, observability, MCP exposure, and airgap deployment.

It is **not** "just a RAG demo." The repo was renamed from `banko-ai-assistant-rag-demo` in April 2026 because "RAG" undersells what it does — the agentic and multi-provider story is the headline.

**Primary audience for the demo**: AWS re:Invent, IBM TechXchange / Think, and enterprise customer POCs (regulated industries and airgap segments included).

## High-level architecture

```
Flask + SocketIO web app
  ├── Multi-agent layer (LangGraph 1.x, CockroachDBSaver checkpointing)
  │     ├── Receipt agent (OCR via tesseract + pdf2image)
  │     ├── Fraud agent
  │     ├── Budget agent
  │     ├── Coach agent (v1a shipped July 2026 — reactive nudges + chat)
  │     └── Supervisor (planned — LLM-routed dispatch, coach v1b)
  ├── AI provider abstraction (banko_ai/ai_providers/)
  │     ├── watsonx.ai (DEFAULT, also default classifier model)
  │     ├── OpenAI
  │     ├── AWS Bedrock (internally identified as "aws", not "bedrock")
  │     ├── Google Gemini
  │     └── Ollama (local models; airgap default granite3.3:8b)
  ├── Vector RAG (SQL on per-user C-SPANN cosine indexes,
  │     384-dim all-MiniLM-L6-v2 embeddings — local, no API key)
  ├── Cache layer (3 tiers: query, embedding, vector_search, all in CRDB)
  ├── CDC intake (spending signals through the /api/cdc/signals webhook
  │     or the Kafka consumer in banko_ai/coach/; settings in the coach group)
  ├── Platform view and load simulator (workers/traffic.py on its own
  │     banko-load pool, /api/v1/platform, banko-ai load; chaos control
  │     plane and CockroachDB HTTP API clients in banko_ai/clients/)
  └── CockroachDB (v25.4.0+, vector indexes are GA, row-level TTL for
        checkpoints and signal/nudge tables)
```

A fuller architecture diagram lives in the internal design docs (local-only, see Repo layout).

## Tech stack quick reference

- **Python**: 3.11+ (3.12 recommended). 3.10 was dropped for 2.0: it reached end of life in October 2026, and pillow 13 and filelock 4.2, which close known vulnerabilities, require 3.11.
- **CockroachDB**: 25.4.0+ (vector indexes are GA). The compose files start v26.4.1 (`COCKROACHDB_VERSION`), and a single node started for a local test is v26.4.1 too.
- **Embeddings**: `all-MiniLM-L6-v2` via sentence-transformers 6.x (384-dim, local). Each major jump (3 to 5 in July 2026, 5 to 6 in October 2026) landed only after `tests/test_embedding_parity.py` showed identical vectors, so nothing stored in CRDB needed re-embedding.
- **Agent framework**: LangGraph 1.x
- **Checkpointer**: `langchain-cockroachdb` 0.6.x, for `CockroachDBSaver` only (the legacy vector store and chat history routes were removed in October 2026 because they were unauthenticated and read across users; semantic search is plain SQL). Its calls retry transient errors themselves (40001, dropped connections including the TLS "unexpected eof", the i/o timeout after a canceled session), so never wrap them in banko's `@db_retry`, or the attempts multiply. Checkpoint reads and writes run concurrently on the assistant's pool, which connects as `banko-checkpointer` in `SHOW SESSIONS` and opens up to `CHECKPOINT_POOL_SIZE` connections (default 16). A full pool raises `PoolTimeout` after `DB_POOL_TIMEOUT` seconds, and nothing retries that. Keep `prepare_threshold=0` on the pool. Since 0.6 row-level TTL keeps what a live thread still uses: blob rows outlive their checkpoints by a tenth of the interval and each write brings forward the ones still in use. `get_saver()` does no TTL work. `checkpoint.keep_ttl()` does, in the `checkpoint_ttl` warm-up step (background, after `assistant`, skipped with `--no-data`): it calls `enable_ttl()` only when `checkpoint_blobs` has no TTL, lacks the 0.6 setting or is paused (a first boot, a database 0.5 set up, a run that stopped partway). The run pauses TTL, waits about 15 seconds for other savers and resumes, and with the setting already in place it is still three schema changes, so never call it on every boot or from `get_saver()`. It reuses the interval the database already has, so an upgrade deletes nothing an earlier boot kept; `CHECKPOINT_TTL_DAYS` only sets a database that has no TTL. A run that fails, or leaves the setting not current, fails the step and the next boot tries again.
- **Web**: Flask 3.1.3 + Flask-SocketIO + eventlet (prod) / threading (dev)
- **Dep manager**: `uv` (lockfile is `uv.lock`; the deprecated vertexai SDK is gone, google-genai 2.x covers both Vertex and the public API). `make audit` checks the lock and the vendored browser libraries for known vulnerabilities; CI runs it on every PR, on pushes to main and weekly. Dependabot uses the uv ecosystem, so its PRs re-lock; they still get a local rebase and smoke before merge.
- **Testing**: pytest, ruff, mypy (mypy is advisory, see Open bugs)
- **Docker**: multi-arch (amd64/arm64), images on Docker Hub at `virag/banko-ai-assistant`

## Conventions and gotchas — do not relearn these the hard way

These come from prior development pain (mostly from droid sessions Feb-Apr 2026). Honoring them prevents reintroducing fixed bugs and avoids known footguns.

### LLM and AI

- **Default provider is watsonx**. Override via `AI_SERVICE=openai|aws|gemini|ollama` env var. Aggregation questions (how much, how many, average) never reach the LLM for math: the intent classifier routes them to SQL and the model only narrates the pre-computed figures. The largest or smallest purchases ("my biggest purchase last month", "top 5 biggest purchases in October") go to SQL the same way: SQL orders them and code writes the card, with no model call in English. That route takes a question only when it accounts for every word of it (a lead-in, how many, the size word, a category or merchant, purchase, transaction or charge, a place, a window it can read). One word left over ("that month", "on it", "under $100", "ever", a second clause) and the question goes on: to the totals when it asks for one, which account for every word themselves (next entry), to the planner otherwise. A subject that is no category and none of the user's merchants, or that has no purchases, goes on to the planner as well, the way an unknown place does on the visits route, and "the biggest purchase" with no window or place of its own goes there once the thread has turns. These questions used to reach the planner, whose tools return the rows most like the wording or the most recent ones, never the largest (a month's rent was left out, and a June purchase was once named as last month's); `spend_summary` now carries the three largest purchases next to its recent rows for the questions that still go there. The totals, the size route and the visits read the same windows: "in October", "for October", "in October 2025", "in 2025", "the last two weeks", "the past year" (the 365 days up to today; "last year" alone is the calendar year), "year to date", "for the year". "Up to today" and "so far" name none. A window none of them reads leaves a total or a size question with the planner: a total used to fall back on the last 90 days, which only its card said. A spending category or one of the user's merchants asked for alone or as its purchases ("coffee", "my coffee expenses", "show me my coffee purchases", "starbucks", "purchases at starbucks") goes to SQL as well, and code writes its card: see "A category or merchant named alone" under Foundation layers. Visit questions (did I go to X, when did I last go to X, how often do I go to X) take the `visits` route: SQL counts them and code writes the card, with no model call in English; a place that is none of the user's merchants goes on to the planner. The UI provider switcher must key on `AI_SERVICE`, not model name — there was a real bug where the watsonx logo kept showing even when OpenAI was active because display logic keyed on model.
- **A total accounts for every word of its question** (`classify_aggregation` in `utils/intent_classifier.py`). A total's own words name nothing: who asks and the asking ("can you tell me", "I'd like to know": `_ASKING`), a greeting or a tag (`_HELLO`), the counting, the spending and its rows (`_TOTAL_WORDS`). The dates are read and cut out. What is left is what the total is of: "coffee total", "how much coffee" and "how much is my rent" used to drop it and answer for all spending, and so did "how much do I have" and "how much do I spend a month". Words left over make the intent `loose`, and `aggregations.loose_subject` takes them only whole and exactly: a category money is spent on, or one of the user's merchants by its name. Never a near miss ("shipping" is not Shopping), never a name beside other words ("excluding amazon" is not Amazon's total), and not a name that may be something else when it stands alone ("my bills", "my target": the answer cache's `_THINGS` and `_OWN`). Anything else goes to the planner, never to a total over everything. Behind on, for or at a subject is a name by its place and is read as it always was, a near miss included, even when every word of it is one a total calls its own ("at the dollar store"); `_core` only takes off what no name ends with ("on coffee though"). With any other word left over more is asked than its total, and the question is the planner's from the start ("how much can I spend on groceries"; `more_than_a_total` says so to the router, which then does not hand it to a receipt on the table either). Left out of a total's own words on purpose: what points at something (it, that, there, mine), what turns a question around (not, only, more, over, than, everything but), what asks what is allowed, needed or still to come (can, will, should, need, going to), what names a place or a kind (store, merchant), money coming in ("how much did uber pay me"), every number, and every word of time. A window that was read is gone by then, so "last", "month" or "weekly" left over is a window nobody read or a rate, and the dates as one end of a span ("from last month to today", "as of yesterday") are not the window either. A count counts purchases ("how many coffee purchases"), not things ("how many subscriptions", "how many stores"). A total of a category is a money question whatever the money check makes of its words ("total electronics", "how much movies" were turned away), and so is a total at one of the user's merchants, which the graph's route node asks the merchants the process keeps (`_total_at_own_merchant`, only for a message that is a total by its words and was turned away). The other half is as much a rule: a plain total stays on SQL however it is dressed. `tests/fixtures/plain_totals.tsv` holds some 840 everyday phrasings that must stay on SQL, each with its window, and `not_plain_totals.txt` the questions that must never get a total of everything. A word missing from the list sends its question to the planner, which costs three model calls where the total cost one; a word too many answers a question for all spending. So every word in `_TOTAL_WORDS` has to be needed by a row of the fixture or by a total with a subject (`test_every_word_a_total_calls_its_own_is_needed`): to teach the totals a phrasing, add its row first. Slang for spending ("how much did I blow") and whatever else the list lacks is the planner's. The classifier reads no question longer than 300 characters, and the router collapses runs of spaces first: its patterns took minutes over ten thousand of them.
- AWS Bedrock is identified internally as `"aws"`, NOT `"bedrock"` — docstring is inconsistent in places but the env value is `aws`.
- **All LLM calls go through `banko_ai/ai_providers/`** — never import `openai`, `anthropic`, `boto3.client('bedrock-runtime')`, etc. directly anywhere else. This is what makes airgap mode (Ollama) and provider switching work cleanly.
- Dynamic model discovery is the pattern for every provider — never hardcode model lists.
- **What the planner reads decides what it plans, to the character.** Which tool a short question gets is the model's choice, and it turns on very little: when the page size became a setting, the search tool's argument in the planner's tool list went from `limit: int` to `limit: int | None`, and on gpt-4.1 "coffee" went from no tool (so Banko ran its search) to `spend_summary`, in seven runs of seven each way. gpt-4o-mini picked the search with either list, which is why no smoke through the gateway saw it, and a scripted model plans what the test tells it to. So `tests/test_assistant_planner.py` holds a copy of the tool list (`describe_tools()`): a changed argument, type or description fails there first. Change it on purpose, and then ask the model the hosted instance runs (gpt-4.1 through the gateway) a few short questions again and look at the tools it picks ("coffee", "my coffee expenses", "starbucks", "groceries"). Even on one prompt the choice is close to arbitrary (on 2.0.0's, "coffee" and "groceries" got the search, "my coffee expenses" and "starbucks" a total), so nothing an answer shows may depend on it: see the plan under an answer, in Foundation layers.
- Some models behind the OpenAI API (and whatever a gateway names them) take only their default temperature and refuse any other with a 400. `ai_providers/openai_temperature.py` learns that from the refusal: the request goes out again without a temperature, and the model is remembered for the process once that request is answered (never on the refusal alone, which may be about something else). Build OpenAI chat models through its `chat_model()` (the factory does) and never keep a list of such models.
- LangGraph checkpoints auto-expire after 7 days via CRDB row-level TTL (`CHECKPOINT_TTL_DAYS`). A database keeps the interval it first got; to change it, run `enable_ttl()` with the new one once, from one process.
- **A model is called only for something a person asked for or will read**: a chat answer (and, behind it, the memory a message such as "I prefer window seats" leaves), a receipt's fields, the explanation of a flagged purchase, a coach nudge. Boot, seeding, page views, health endpoints, the standing workers and the load simulator make no model calls: at boot the provider sees only a reachability check that uses no tokens (the one exception is finishing a nudge that a restart interrupted in the last hour). A receipt costs one call, reading its fields; the fraud agent asks the model to explain only a purchase that tripped a signal, and the budget check asks it nothing. A purchase with no signal gets a line built from the checks that ran (`no_signal_reasoning`): a check that could not run is named first, never counted among the clean ones, and the receipt card says so as well (`fraud_words`). When the model cannot explain a flagged purchase the line is its signals (`signals_reasoning`), never the provider's error. The coach makes two calls per signal, and skips signals for the load simulator's `load-` customers before claiming them, so the boot replay never meets them. When a change adds a model call, say what it costs.

### CockroachDB and vector search

- Vector indexes are C-SPANN, cosine ops (`<=>` operator). **Do not use L2** — the codebase migrated away from it.
- No `CAST` in vector queries — the `<=>` operator on a `VECTOR(384)` column does the right thing directly.
- Pre-v25.4.0, the `feature.vector_index.enabled` cluster setting was required. GA now — no longer needed but harmless to set.
- User-specific vector index `idx_expenses_user_embedding` exists; all per-user vector queries should filter by `user_id` to use it.
- Purchases are kept apart by user, and by region on a multi-region database, and nothing may read them across users to answer for one. Two rules keep it so. No plain index on `expenses` holds every user's rows: `idx_expenses_merchant` and `idx_expenses_shopping_type` did, nothing read purchases across users by either, and for a user it had no statistics on CockroachDB read a category "since ever", a category over a year or a merchant's visits through them (every user's coffee, in every region when no region was named). They are out of the registry, and `_dropped_index_upgrade` drops them from a database that has them on its next boot (`DROPPED_INDEXES` in `db/schema.py`: the registry only adds what is missing, so an index taken out of it needs an entry there). And a statement on one user's purchases names the index that leads with the user: `FROM expenses@idx_expenses_user_date` (or the vector index above). `tests/test_per_user_reads.py` takes the statistics away, runs what the assistant, the pages and the coach run, and reads the plan of every statement on purchases they sent; it also holds `banko_ai/services`, `assistant`, `coach` and `utils/aggregations.py` to the rule by their text. A lookup by `expense_id` names no index. `resolve_category` runs no statement: its near match is against the catalog's labels, where it used to read every label in the table once per process.

### Receipt OCR

- Tesseract MUST be in PATH or receipt upload silently returns "Unknown" for all fields. This bit us — see `scripts/setup_system_deps.sh` for installer.
- Every page is read through `document_tools.read_text`. Left to lay a page out by itself, tesseract can drop whole lines of a faded receipt, the total among them; as one block of text (`--psm 6`) it keeps them. So a page whose first reading holds no amount is read once more that way. Do not "improve" the image first: on a faded thermal print, thresholding, thickening and sharpening each produced totals that were wrong and looked right.

### Caching

- 3-layer cache: `query_cache` (semantic, 0.75 similarity threshold), `embedding_cache` (per-provider — provider is part of the unique key, this was a bug), `vector_search_cache`.
- Cache hits are reported via `/cache-stats` (not `/api/cache/stats`, which does not exist).
- These are the 1.x tables behind the legacy endpoints. The assistant's own caches (`answer_cache`, `search_cache`) and how they match questions are under Foundation layers: "Answer cache matching".
- TTL default 24h; configurable.

### Frontend

- Agent dashboard activity feed must reflect REAL agent activity. The user has been bitten by canned/hardcoded demo lights — never ship a dashboard with synthetic events.
- Agent activity is read through `/api/v1/agents`, which answers for one user. The old `/api/agents/status`, `/activity` and `/stats` routes were removed in November 2026: they needed no sign-in and returned every user's activity, fraud reasoning with its merchant and amount included. Never add an endpoint that reads `agent_decisions` or `agent_state` without scoping it to a user.

### Documentation

- ONE end-to-end doc for any new feature, not a sprawl of `FEATURE_X.md` + `FEATURE_X_NOTES.md` + `FEATURE_X_FIXES.md`. The user has explicitly deleted droid-era doc piles. Keep `docs/` lean.
- README target: ~250 lines, with the architecture diagram and the page screenshots (docs/images/<page>-light.png and -dark.png, taken from a seeded database on watsonx). Image links are absolute raw.githubusercontent.com URLs so PyPI renders them. In the repository they point at main; the release workflow runs `scripts/pin_readme_images.py` before it builds, which moves them to the release's own tag, because PyPI keeps a release's text for good (the 1.3.2 page lost both of its images the day main dropped those files). `tests/test_readme.py` checks that every file the README links is in the repository, and that no link is relative: PyPI and Docker Hub show the README too and resolve nothing against the repository, so files are linked as `github.com/.../blob/main/...`. ### Foundation layers (v2)

- CLI: `banko-ai doctor` checks what a demo needs, one line each and exit 1 on red. Its provider line asks the model one real question (a login token or a model list is not an answer: an account that is out of quota still hands those out, and a local model can be listed and fail to load) and says why not in fixed words, never the error's text. Its database line also fails for a database name that does not exist, which CockroachDB accepts at connect time; `seed`, `reset` and `migrate` run the same services as the app. There is no ownerless sample data any more (personas and signups are seeded); removed 1.x commands and flags stay as hidden pointers to their replacements (`_moved` in cli.py).
- Docker: the image sets HOME=/app and HF_HOME=/opt/banko/cache/huggingface, both group 0 and group-writable, so it runs under any UID (OpenShift). Boot-test a release image with `--user 12345:0` and run scripts/smoke.py through it.
- Clock: every date Banko stores is a UTC date, so "today" is `banko_ai/utils/clock.today()` everywhere: the assistant's windows, the planner prompt, the coach, a receipt with no date. Never `date.today()`, and never `datetime.now()` without a zone (guardrail test `tests/test_one_clock.py`). West of UTC the machine's calendar is a day behind every evening, and a purchase made then fell outside "today" and "the last 30 days". The suite runs in UTC (`tests/conftest.py`), and a test that has to disagree with UTC uses the `another_day` fixture.
- Settings: `banko_ai/config/settings.py` is the only reader of environment variables (a guardrail test enforces it). Add a knob as a field there; `banko-ai config --docs` renders it.
- Database: use `banko_ai.db.engine.get_engine()`, `run_transaction()` or `user_session()`. Never call `create_engine()` or `.dispose()` elsewhere (guardrail test). Bulk writes are set-based; never `executemany` on an autocommit connection (psycopg 3 turns it into one implicit transaction).
- psycopg 3 binds server-side, and CockroachDB rejects placeholders in `EXPLAIN`. Any EXPLAIN with parameters goes through `psycopg.ClientCursor` (see `explain_aggregation` and the vector search explain).
- Schema: every table, index and locality lives in `banko_ai/db/schema.py`. Boot runs one SELECT when the fingerprint matches. New columns on existing tables must be nullable or have defaults. Existing indexes are matched by name only, so an index whose definition changes under the same name needs an upgrade in `UPGRADES` (`_vector_ops_upgrade` rebuilds the L2 vector indexes a database first created before 1.0.36 still carries; a cosine search pinned to one is an error). A boot that finds the fingerprint current runs nothing, so an upgrade that must reach databases whose rendered DDL did not change raises `REGISTRY_VERSION` (3 came with that one).
- Boot: slow work goes in the warm-up steps in `create_app`, reported through the app's `Readiness`; nothing slow runs before the server listens. Pages wait for the `schema` and `personas` components. A database name that does not exist (SQLSTATE 3D000, `db.engine.missing_database`) is said in one plain line by the gate's log, the health detail, the getting-ready page and doctor. A database emptied under a running process (a cluster rebuilt from the chaos stage) is set up again without a restart: `workers/schema_watch.py` asks `schema_state()` every `SCHEMA_WATCH_SECONDS`, and at once when any statement fails with 42P01 (`db.engine.watch_missing_tables`), and `_set_up_database_again` runs the schema, personas, locality, seeding and checkpoint-table steps again, behind the same getting-ready page. Anything new that caches a fact about the database across requests must be forgotten there. "Missing" means `banko_meta` is not there or holds no fingerprint, nothing else (a role that may not read it raises). The checkpoint tables are made again by whoever needs the saver first (`checkpoint.tables_gone()`), so a question right after the gate reopens waits for them and a failed attempt is tried again. A 42P01 from a database that still has its schema stays an ordinary error. A step started again belongs to the newer warm-up lane (`Readiness.set(..., lane=)`). The watch is off under `BANKO_SKIP_AUTOSETUP`.
- Sign-in: off by default, a username with no password (the persona picker). With `IAP_AUDIENCE` set, a deployment behind Google's Identity-Aware Proxy signs everyone in as themselves: `web/iap.py` verifies the `x-goog-iap-jwt-assertion` header (ES256 against Google's keys, issuer, audience, expiry) on every request, and any failure means not signed in, never an error page. Never read `x-goog-authenticated-user-email`, which anything that reaches the app without passing IAP can forge, and never let a posted username become an identity in this mode (`/login` and `/signup` ignore it). The account is keyed on the assertion's `sub` (Google's stable id for the user), never the address, so a reassigned address brings no account with it: `services/staff.py` derives the user id as `uuid5` of it and takes the username from the address's local part, stores neither, and makes the account on the first visit through the same start a sign-up gets (`app.extensions["banko_start_account"]`). A history that never finished is started again on the next sight of the account, and one that failed by the next page load. An account this process has seen is remembered for the life of the process, so signing in reads the database once per person and an outage signs nobody out; `delete_users` forgets what it removes. `session["me"]` is the person, `session["user_id"]` whose money is on screen: themselves or one of the catalog personas (`POST /view-as`), nothing else. In this mode nothing is answered for the default persona: a request no assertion vouches for gets 401 on `/api/` (a page goes to the notice at `/login`), an account that cannot be read gets 503 and stays signed in, and both carry no `X-Banko-User`. Socket.IO requests pass none of the request hooks, so `coach.join` checks the handshake's assertion itself. A request that changes something must come from Banko's own pages (`Sec-Fetch-Site`, or `Origin`): the proxy's cookie, not Banko's, is what signs anyone in, so SameSite does not guard it. For the same reason nothing may frame Banko in this mode (`X-Frame-Options: DENY` and `frame-ancestors 'none'` on every response): a click inside a frame is sent by Banko's own script. A user id is a name, never a secret: no route may take one from the request. `tests/test_staff_sign_in.py` walks every route in `app.url_map` without an assertion, so a new route is covered without being named there. The boot log says which sign-in is on. With the setting off again (by choice or by a typo) an account this sign-in made is not opened by typing its name at `/login`. The verifier times its key reads on a clock that only runs forward (`elapsed`), checks an assertion's times against the time of day (`now`), and logs each reason for turning one down once a minute, in its own words. An account nobody has used for `IAP_USER_IDLE_DAYS` (30) is removed at boot and once a day. Only accounts this sign-in made are candidates: they carry a `seen:<user_id>` row in `banko_meta` from the moment they are made, written again at most once a day because that table is GLOBAL (the day is given back when counting), and `DEMO_USER_TTL_DAYS` leaves them alone.

- Content: categories, personas and seed profiles are YAML in `banko_ai/config/defaults/`, overridable with `CATEGORIES_FILE`, `PERSONAS_FILE`, `SEED_PROFILES_FILE`. - Home region: on a multi-region database every account needs one. Without it nothing pins its writes (rows land wherever the load balancer sent each one) and no read can name a region, so every statement looks in all of them. Sign-up asks; an account the Google sign-in makes starts in the database's primary region (`services/home_region.default_region`). `home_region.set_home_region` moves an account: it points `users.home_region` first, then brings the rows of every REGIONAL BY ROW table over in short batches, as the owner, pass after pass until one finds nothing (a write that began earlier can land in the old region late), and calls `regions.home_region_changed` so routing and `read_region` look again. Settings offers it (`POST /api/v1/me/home-region`), for one's own account and never a persona's, whose region the personas file sets again at boot.
- RLS: policies on six tables only, accounts, ledger_entries, transfers, goals, user_budgets and chat_threads (`RLS_TABLES` in `db/rls.py`), for the `banko_app` role; request-path services resolve `url` with `rls.request_url()`. Never add RLS to a vector table.
- Assistant: every chat turn runs the LangGraph graph in `banko_ai/assistant/graph.py` (ingest, route, aggregate | visits | receipt | memory | offtopic | plan | more, respond, learn), checkpointed per thread with `CockroachDBSaver` (`assistant/checkpoint.py` owns its psycopg pool). Routing is deterministic (`assistant/router.py`); only open questions reach the JSON planner. An answer from SQL needs no embedding model. Memories are recalled where a model writes from them (`_recall`: in the planner's node and a receipt's, once their cache has said no), and the router asks whether a message is about money (`is_financial_query`, which embeds a message whose words say nothing) last and only where a route turns on the answer. Both ran first on every turn, so on a process that had just started "coffee" waited for the embedding model twice: up to `WARMUP_WAIT_SECONDS` in the recall, then again in routing. Models are reached through `ai_providers/streaming.py` (`ProviderChat`), and tests use `tests/_chat.py` (`ScriptedChat`), never a live model. A lookup that raised must never read as "you have none": with no other facts the reply is the fixed `LOOKUP_FAILED` line and no model writes one, otherwise `LOOKUP_PARTLY_FAILED` follows the answer. Only a tool that raised counts: arguments the model got wrong must decline instead (an args constraint, a `ToolError`, or an empty result such as `duplicate_check` gives a made-up id). A total's card is the figure, its breakdown and the latest ten purchases; the breakdown (`top_categories`, `top_merchants` in `utils/aggregations.py`) is summed by SQL over the whole window and is what the insights prompt quotes. Nothing is ever added up from the rows a card lists: those are only the latest ones. A conversation with a receipt on the table stays away from the answer cache (the same words about another receipt mean something else); its answers, on the receipt route and the planner's, are kept in `search_cache` under a key that holds the receipt (`_receipt_scope`, `_receipt_key` in `graph.py`), never for words that lean on the turn before. The router takes a merchant's own words as a pointer to the receipt, not a word in its name that names a category: "coffee expenses" beside a Blue Bottle Coffee receipt is about all coffee. An answer from the planner shows a plan as the SQL routes do, whichever tool the model picked (`_plan_of` in `graph.py`): of its semantic search when there was one (the search "show more" continues), else of the last lookup that can say how it ran, a total from `spend_summary` (`tools.spend_plan`) or a merchant's visits from `merchant_history`. It used to be the search's alone, so "coffee" showed how CockroachDB ran it on one model and nothing on the next. A plan is always of the statement that ran: one builder writes the WHERE of the statement and of its EXPLAIN (`_where_and_params`, `_visits_where`, `semantic_sql`), and both name the region `read_region` gives (the totals tool and the visits statement named none and read every region; the search named it and its plan did not). A lookup that was declined, or any other tool, brings no plan, and the window says so. On the full page the trace panel names the question it is about and that answer is marked (`traced`), and an upload makes its thread before it posts, so a question asked while the receipt is read lands in the same conversation. The panel also opens in a window of its own (`/assistant/trace`, `templates/pages/trace_window.html`: no shell and no data of its own), where the query plan keeps its lines and the text can be made larger for a second screen. The window holds only what the Assistant sends it: each answer that lands and each answer whose "How this was answered" is clicked goes out as plain data on a `BroadcastChannel` named `banko-trace` (`Banko.sendTrace`, `traceOf` in `assistant.js`), and a window that opens or is reloaded asks for the last one. Anything new the panel shows has to be added to `traceOf` to reach the window. A plan names the user it ran for, so the window does not keep one past that user's turn at the keyboard: every page with the Assistant says on the channel whose account is on screen, the sign-in page says when nobody is signed in (`auth/login.html`, from the session), and a window showing another account's answer goes blank.
- Platform: the load simulator (`workers/traffic.py`) runs `workers/workload.py` operations through the real services on its own `banko-load` pool (`get_engine(url, pool_size=)` with an `application_name` in the URL; never a second `create_engine`). Its customers are `load-` demo users built from the seed profiles (`services/load_users.py`), and every user deletion, load users, `clear-demo-users` and the demo user expiry alike, goes through `services/users.delete_users`, whose table list comes from the schema registry. Each customer runs through their home region's own pool (`with_gateway_region`: get_engine keeps connections whose `gateway_region()` matches, re-asking the load balancer; after a miss it takes connections as they land and tries home again after 15 s, or 5 minutes for a region its URL never reached), connected as the owner rather than `banko_app` (on v26.3 RLS plans every statement after a round trip to a system range, 60 to 116 ms from gateways away from it, and keeps `crdb_region` filters out of the scan). A customer has one operation in flight at a time, and the load pools end a statement after `LOAD_OPERATION_TIMEOUT_SECONDS`. Signed-in users are routed the same way: `read_session`, `user_session` and `run_transaction` use `engine.routed()` (`ROUTE_BY_HOME_REGION`); any other per-user connection is `get_engine(routed(url, user_id))`, and a `run_transaction` for a user passes `user_id=`. `tests/test_home_routing.py` covers the request path area by area (one unrouted totals query took 703 ms against 12 ms at home). Cache hit and miss counts go to `cache_stats` (primary region) from a background writer, never inline. The read services name the region (`region_pin`) only through `regions.read_region`: not on the RLS app URL, only when money tables are REGIONAL BY ROW, and only for users whose money rows all live at home (`rows_home`, primed for load users at start). On a database created multi-region, the expenses and transfers primary keys and the transfers idempotency key lead with `crdb_region` (an INSERT ... ON CONFLICT, or any insert into a table with vector indexes, otherwise checks a global key in every region even for `gen_random_uuid()`) (`Table.regional_primary_key` and `regional_constraints`); `scoped_key()` picks the ON CONFLICT target and such rows get a region that never depends on the gateway (`SCOPED_REGION_VALUE`). The transfers key is scoped in place on older multi-region databases; the expenses primary key is not (CockroachDB 26.3 fails to rebuild it in place). Transfers and card payments keep their idempotency keys; purchases and deposits let the database pick ids and report a commit lost in flight as `ambiguous` instead of retrying it. On a REGIONAL BY ROW table a client-chosen key costs a uniqueness check in every region, and on `expenses` even a `gen_random_uuid()` default keeps that check because of the vector indexes. `run_transaction` retries a connection lost before COMMIT even for non-idempotent work and marks a failed COMMIT with `at_commit`. Declines are business outcomes, not errors. `/api/v1/platform/live` never touches the database; `/cluster` and `/data` are background snapshots. A card's lookup that fails must not read as an empty result: `cdc_status()` returns `changefeeds: None` when the jobs could not be listed and `[]` when there are none (a type error in that statement hid behind a swallowed exception as "No changefeeds"). Node liveness comes from the chaos plane or CockroachDB's HTTP API, never `crdb_internal` (restricted on v26), and a derived HTTP API address is trusted only when its nodes' regions match `SHOW REGIONS FROM CLUSTER`. `SHOW RANGES ... WITH DETAILS` costs about 7 s a table on the 3-region cluster, so it is background-only. Metric windows cover complete seconds. Charts follow the dataviz skill: one axis per chart, colors checked with its validator in both themes.
- Assistant data: `receipts` (not the legacy `documents`), `chat_threads` (RLS), `memories`, `answer_cache`, `search_cache`, `assistant_actions`. Per-user vector lookups go through `services/_vector.nearest`, and semantic search through `transactions._neighbours`. Both pin the index and rank the user's rows exactly whenever the index returns fewer rows than the user has, not only none (cockroachlabs/cockroach#13756; on the 3-region cluster one user's index returned the same single row for every query). Cache keys include the user's data version.
- A category or merchant named alone: a spending category or one of the user's own merchants, asked for bare or as its purchases, optionally for some dates, is one shape (`caches.subject_asked`), and the router sends it to SQL. "coffee", "coffee expenses", "my coffee spending" and "show my coffee purchases" are one question, so are "starbucks" and "purchases at starbucks" for someone who bought there, and "coffee this month" is "coffee expenses for this month". A category goes through the totals as its purchases (`AggregationIntent("purchases", ...)`, for the days it names or for all time, `EVER`): the figure and the breakdown come from the totals statement, the latest purchases as the Transactions page lists them (`_purchases_listed` in `graph.py`), a page as long as the asker set, and code writes the card. A merchant goes through `visits`. No model is called in English, so the answer is the same on every model and comes with the provider out of reach. These used to be the planner's, whose model gave "coffee" a search on gpt-4o-mini and granite and a total of 31 days on gpt-4.1. Show more under the card asks the transactions API for the category's next purchases (`meta.search` with an empty `q`), and a typed "show more" the `more` route, which lists them the same way. A category nothing was bought under says so, and no model is asked. The card is kept (`_card_key`, `_kept_card`, `_keep_card` in `graph.py`): in `search_cache`, under what was asked for (the kind of card, the category's label or the merchant's words, the dates the statement read, the language, the page length) and the user's data version, never under the words. Asked again, or in other words, it comes back with no statement on the purchases: it says cached, says whose answer it is when the words differ, brings the page Show more goes on from and no query plan, because no statement ran. The card for the largest or smallest purchases is kept the same way. A card the model could not translate went out in English and is not kept as the translation. Raise `CARD_KEPT` when a card's words or layout change. It is the same question wherever in a conversation it is asked. Read as a short follow-up there, "coffee" asked twice in one chat was a card from SQL the first time and the planner's the second: three model calls, and an answer no cache keeps. The same holds for a total of a category or at one of the user's merchants whose words say nothing about money ("total electronics", "total spotify"). A bare name beside a receipt may be a line of it, so there it is the planner's, and what it is told is kept under no words. Words that point back are the next entry. The router knows nobody's purchases: the graph's route node hands it `is_merchant` (`_own_merchants`), asked only for a few words that could be a name ("hello" costs one read of the user's data version and, once for each state of their money, of their merchants), and a read that fails says no. `merchants_of` reads a user's merchants only when a name that is no category asks (inside the home region when a read may name it), and keeps them in the process by database and user under the user's data version, for at most `_MERCHANTS_SECONDS`: another process may delete an account and make it again, and nothing tells this one. `forget_merchants` drops them where the versions start over, in `delete_users` and `_set_up_database_again`. A stored name loses a leading "the" or "my", as the shape takes them off a question ("home depot purchases" finds The Home Depot). A merchant with one of Banko's own words in its name is asked for only in words that can mean nothing but the shop (`_OWN`, `_only_the_shop`): "my target" may be a savings target and "spending on target" may ask whether the spending is on target, while "target purchases" and "spending at target" are the shop. At and from are a merchant's alone: "purchases at the restaurant" names one restaurant, not the category. A category's name that is a thing of its own when it stands alone ("bills", "phone", "subscriptions": `_THINGS`) stays the planner's, and "show me movies" asks for films, not for what was spent on them ("show me my movies" is one's own). Like the other SQL routes, the shape takes a question only when it accounts for every word of it. Dropping "small words" from every question was tried first and no list of them was small enough ("show my savings account" is not "show my savings account transactions", "did I get a refund" not "can I get a refund"), so never widen the shape by a list of words that may be ignored, and keep questions out of it ("what is my coffee spending" asks how much) and every verb but show, list, display and view ("find me flights" asks to book). Beside a receipt a category's purchases are about the category, not a line of the receipt ("my coffee expenses" with a coffee on it).
- What a model writes about the user's money is read before it is shown (`assistant/figures.py`). SQL computes the figures and code writes the cards, but a model still writes the planner's answer, the answer about a receipt, the observations under a total and the translation of a card. Each is read as it streams (`figures.Reader`, through `figures.released`): a sentence or line goes out when it is whole and every figure in it is one the model was given (`figures.given`: what the lookups found, the question, the conversation, the memories, the context), and a sentence with a figure from nowhere is never shown. The answer then says so in a fixed line (`FIGURE_LEFT_OUT`), the trace names the figures ("Figures check"), `meta.figures` lists what was left out, and the answer is not cached, so the next ask can get all of it. The rules, each with the answer that taught it (gpt-4.1 and granite3.3:8b, 34 questions each): an amount is checked to the cent; an amount may be the sum, the difference or the average of two figures that were given, because to the cent that leaves no room for a made-up one, so the arithmetic is checked, not refused; a count has to be given as it is (small numbers add up to anything); a count in words is no figure ("the past four months" was right and was held back); a percentage counts as given only when it was given as one (`_PERCENT_NAME`, a share between 0 and 1, or its sign in a text), never because an amount has the same digits (granite's "57%" stood beside a $57.00 purchase and was 54%); a share that was not given stands when it is the share of two figures written in the same answer, and its sentence waits for them ("22.99% … $946.15 out of $4,114.88"), since of all the figures given some two make nearly any percentage; a month named "2026-09" is given as "September 2026"; "Nov 1–23" is two days; a comma before three digits groups thousands and nothing else ("$8,600" read as 8.60 as well stood on the strength of an $8.60 coffee); a footnote mark ("[1]", "[Cite: 2]"), a list's numbering, a time, an id and a rank are no figures. It reads figures, not meaning: a given figure can still stand in a sentence that says the wrong thing about it. A card's translation that changed, added or lost a figure is not used: the English goes out (`_translate`, `figures.translation_keeps`; a day may be written the language's own way, and scripts written without spaces are read). Cached answers carry a mark that they were read (`_shape`; `CARD_KEPT` and the narrative key moved with it), so nothing kept before is replayed. When a rule changes, read real answers again before shipping it: a scripted model writes what the test tells it to. Not read: coach nudges and the fraud agent's explanation, which have their own prompts. A test that scripts a translation has to keep the figures, as a real one does (`tests/_chat.reworded`).
- A follow-up to an answer from SQL is asked of SQL (`router._the_question_before`). After "how much did I spend on restaurants last month?", "what about coffee?" is that total of coffee (the same operation, the same days, the other name), "and this month?" is it for other days, and "what about coffee this month?" changes both. After a card for a category or a merchant the other name gets its own card (a category its purchases, a merchant its visits) for the days the card before was for, and none when it named none. The graph keeps what a turn asked SQL (`_asked`: operation or card, subject, days, how many) as `asked`, hands it to the next turn's router as `last_asked`, and a visits route carries its days in `Route.window`. "Up to today" is never carried: a card for all time keeps no days, so the follow-up is for all time as of its own day. Paging ("show more") keeps it; a turn the planner, a receipt or a memory command answered ends it, and so does a route that handed the turn on to the planner. Only words that point back ("what about", "how about", "and", "also", "same for", a trailing "too" or "as well") followed by a category, one of the user's merchants, days the totals can read, or a name with its days: the shape accounts for every word (`subject_asked`, `only_days`). "What about it?", "and why so much?", "what about my budget?" and "and the month before?" are still the planner's, as is every follow-up beside a receipt or in a conversation opened from a nudge or a transaction. Left to the planner, a model read the conversation, chose the tool and the days, and its answer was kept nowhere.
- Answer cache matching: which earlier question's answer may be replayed is `CACHE_MATCH`, and each person's own choice: `exact` (the default) or `similar`. A category or merchant in other words was a third way (`words`, the default while the planner answered those): they are read from SQL now and their cards are kept under what was asked for, not under words (see "A category or merchant named alone"), so the answer cache never sees them. The setting reads `words` as `exact`, Settings does not offer it, and the answer cache no longer reads the shape: `get_answer` knows `exact` and `similar`, and the key beside a receipt holds the question word for word and nothing else. What the words matching still joined on the day it went was a thing asked to be shown ("show me coffee", then "list coffee": the planner's, because "show me movies" asks for films), and only for whoever chose similar. Similarity decides between those now, as between any two questions. `answer_cache.thread_id` served the words matching alone and is no longer written or read; the column stays, because dropping one rewrites the table, vector index and all. Every question the cache sees is matched word for word unless similar is chosen. Dates are read as of the day each question was asked (`created_at`, which is the turn's day, `TurnDeps.day`, because the write runs behind the answer): "any odd charges this month" kept on the 31st does not answer on the 1st, and a day no window comes of ("due tomorrow", "next week") is only good on the day it was asked. Similarity cannot tell two questions apart: "coffee expenses" and "tea expenses" are 63% similar, "purchases under $100" and "purchases over $100" 95%. So the vector index only brings the nearest `CANDIDATES` and the words decide. `similar` is the opt-in exception: it counts only between two conversations' first questions (similarity knows nothing of what a conversation was about), and `caches.other_ask` still refuses a near question that names other dates or numbers, differs in a word that turns a question around (`_TURNING`) or has the same words in another order. No list of words closes that either ("who do I owe" and "who owes me" pass), and the page says so. A cached answer written for other words than the ones typed says whose it is (`meta.cache`, and the line under the answer), and a similar question that was refused says why in the trace. Beside a receipt every question is matched word for word (`_cached_beside_receipt`, under a key of its own). `normalize_question` keeps what tells two numbers apart ("$12.99" and "$1,299", "> $100" and "< $100", "-$50" and "$50" were one question each) and the marks a script writes its vowels with.
- Personal settings: `services/preferences.py` lists what a person may set for themselves on the Settings page (`SETTINGS`: how the cache matches, purchases per search page, memory). Each stands in for a deployment setting of the same name, which stays the default: only what a person chose differently is stored (`users.preferences`), so a default that changes reaches everyone who never chose. They belong to the person, not to the account on screen (`web/shell.person_id`: behind IAP the account the request's assertion named, also while a persona is viewed), so one person's experiment never changes the answers a colleague gets while showing Maya. That only holds because the settings that change what an answer contains (`Setting.shapes`: page size, memories) are kept with every cached answer and looked up with it (`Preferences.shape`, `answer_cache.shape`, the receipt key): a setting that shapes answers and is not in the fingerprint leaks one person's answers to the next. An answer kept before shapes were recorded carries none; it was shaped by the deployment's settings and counts for whoever has those (`unshaped`), so an upgrade does not empty the answer cache. (Answers kept beside a receipt before it are not found again: their key gained the settings and the dates.) For the same reason how long a cached answer or search is kept is not a personal setting: on a shared persona one person's lifetime would decide how old an answer the next person gets. With no sign-in in front a persona is everybody's, so the personas step at boot and a reset clear its settings. The chat endpoint reads them once (`person_settings`; a failed read is the deployment's settings, never a failed question) and the turn carries them as `TurnDeps.prefs` and `ToolContext.prefs`: code in a turn reads these tunables from there, never from `get_config()`. Only what shapes one person's answers at question time belongs in the list: nothing secret, nothing read at boot, nothing that sets what a question may cost (steps, history window), and never the model, which the page switches for everyone. To offer another setting, add a `Setting` (with `shapes=True` if it changes an answer) and switch its reading site to `prefs`.
- Receipts: `services/receipts.process_receipt` posts through `ledger.post_purchase`; a receipt ends posted, duplicate or failed, never "processed" after a swallowed error. Duplicates are caught within `duplicate_window_days` (default 3 days, `DUPLICATE_WINDOW_DAYS`). The final `receipt` event says `has_thumbnail`, and a page asks for a thumbnail only then (a PDF has none). An upload refused with a 400 logs why: one that arrives with no file part was lost before Banko.

It boots its own server and seeds, so it takes any throwaway database on this machine (`localhost`, any port but 26257) and refuses everything else. The Assistant page is a pane of fixed height: its grid has one row that cannot grow (`grid-template-rows: minmax(0, 1fr)`), or the conversation stretches the row and the message box is cut off below it. Alpine shows an `x-show` element a frame after its condition turns true, so `scroll()` goes to the newest line again after that frame.

## Testing locally (the required path before any push)

```bash
make test-local        # ruff + advisory mypy + pytest (same ignore list as CI)
# Then boot the app and smoke every implemented provider:
#   watsonx, openai, aws, gemini, ollama
```

The pytest target skips the same script style test files CI skips; they need a running app or live creds. The per-provider smoke is automated: boot the app, run `uv run python scripts/smoke.py --url http://localhost:5000 --expect <provider>` (provider shown and answering, a receipt with follow-ups whose new purchase retires earlier runs' cached answers, totals and visits from SQL, a total that keeps the subject it names without on, for or at, the biggest purchase from SQL with no model call, cache on a repeat, a merchant by its name giving the visits card again from the cache, search and show more on a question only a search by meaning answers, a follow-up to a total answered from SQL for another name and then for other days, one category in three wordings as one card with no model call (the first read from SQL, the others and the same word again in its own conversation from the kept card) and more of its list from the database, Spanish, a coach nudge the model wrote when `CDC_WEBHOOK_HMAC_SECRET` and `DATABASE_URL` are in the shell), then restart the app and run it again with `--resume <thread id it printed>`. A check fails when a tool raised behind its answer (the assistant still answers then, and the answer's trace says so). The search check also fails when no search ran, when the answer came from the cache, or when the search found nothing, and a receipt that comes back a duplicate is uploaded again with a new total so the run always posts a purchase. The coach smoke alone is `uv run python scripts/coach/assert_nudges.py` (webhook transport) or `--via sql` (exercises the real CDC path when the cdc-demo stack is up). The rest of the manual pass list: the right provider logo in the header, real dashboard activity, relevant vector search, clean server log.

CI is **not enough**. CI gates on lint/unit/integration, but the multi-provider smoke is a human-driven, locally-run check.
